# The Mission Control Database

## Creation Scripts and Masterdata

Please refer to [DB Schema in Panta](https://open-systems.atlassian.net/wiki/spaces/DOC/pages/20678848/OSDB+DB+Schema+in+Panta) docs page.
- ddl/generated: snapshot of the schema from PROD at some point in the past.
- masterdata: snapshot of master data tabels, as CSV files from PROD at some point in the past.
- changes: changes on top of the snapshot of ddl/generated, using [Liquibase](https://docs.liquibase.com/)
- ddl/src: current source code of various PL/SQL objects
- mappingdata: symlink to autogenerated mapping data (DX audit trail)

## Schema CI

The CI runs:
`bazel test :tests`

This runs a Java Junit/Jupiter test case in the tests directory.
That test uses [Testcontainers](https://www.testcontainers.org/) to spin up the container DB (see above),
and runs the Liquibase changelog against it. Then makes checks that everything applied cleanly.

### Running the CI locally
In order to run the CI locally you need Docker installed.


### Modifying or regenerating the ORM layer
The validity of the DX ORM layer is checked by regenerating all DB-dependent classes from a new container with the changelog of 
your branch applied. The CI script [ci-verify-orm.sh](tests/ci-verify-orm.sh) does that in the ORM rebuild check BuildKite step.

If it fails, run [update_dx_orm.sh](tests/update_dx_orm.sh) manually and commit all resulting changes
to //dx/java/core (and resolve all conflicts and failing tests there) before merging a PR. 

Adding `[nolint]` to the commit message is recommended, because the automatically generated Java classes violate some of megalinter's standards.
