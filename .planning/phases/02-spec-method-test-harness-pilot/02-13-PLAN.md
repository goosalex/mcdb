<objective>
Close the phase: run everything together, prove red→green across the whole pilot in one scripted
gate, and turn seven scattered FINDINGS files into the two documents the next phases actually need.

Purpose: Up to now, each package went green in its own database, and some assertions stayed red
waiting for a cycle sibling. This plan is the first time the entire pilot — 7 packages, ~76 public
routines, the four-package TT cycle group — stands up together and is judged as a whole. It is
also where the phase answers the only question that really matters: **is this method fit to be
applied to the remaining 44 packages?** An honest "yes, with these three template changes" is
worth vastly more than an unqualified "yes".

Output: `run-all.sh`, the red→green evidence, `PHASE2-FINDINGS.md` (Phase 3's opening brief), and
`METHOD-REVIEW.md` (Phase 4's go/no-go).

  <action>
    Run the red→green gate across the ENTIRE pilot, not package by package:

      `bash migration/test/redgreen.sh --db mcdb_phase2_rg --install migration/pgsql`

    It builds a fresh database from the template WITHOUT any translation, runs the full suite (must
    FAIL — hard, with "function does not exist" everywhere), then rebuilds, installs everything, and
    runs again (must PASS). Its built-in guard aborts if the RED phase does NOT fail, which is the
    single most valuable thing it does: a suite that passes against a nonexistent implementation
    proves nothing at all.

    Capture both logs and write `migration/test/REDGREEN-EVIDENCE.md`:
      - the exact command;
      - the RED run: exit code, the per-package table (all FAIL), and a representative error;
      - the GREEN run: exit code, the per-package table (all PASS), test counts;
      - the delta: N assertions that failed before and pass now.

    Then — and this is the part that gives the evidence teeth — run a **mutation check**. Pick three
    translated routines from different packages (one with a `STRICT` SELECT INTO, one with an
    empty-string normalisation, one with an exception handler). For each, make a single deliberate
    wrong change of exactly the kind the pilot exists to catch:
      - remove `STRICT` from one SELECT INTO;
      - remove one empty-string normalisation;
      - swallow one exception that the spec says re-raises.
    Run the suite after each. **Each mutation must be caught.** Revert each.

    This is the difference between "the tests pass" and "the tests would notice if the translation
    were wrong". A suite that goes green on the real translation but ALSO goes green with `STRICT`
    removed has told you nothing, and the whole phase would be theatre. Record all three mutations,
    what was changed, which assertion caught it, and the exit code — in REDGREEN-EVIDENCE.md.

    If any mutation is NOT caught, that is a genuine gap in the test suite. Fix it by ADDING a test
    (with a clause citation), record it, and re-run. A missed mutation found now is a Phase 4
    disaster avoided.
  </action>
