<objective>
Derive specs from Oracle source for the three small pilot packages, and write the tests that
verify those specs — before any translation of them exists.

Purpose: These three are the pilot's control group. `MSS.OSAG_DBPROP` and `AUTH.OSAG_AUTH`
are small and statically clean, so if the method cannot work here it cannot work anywhere.
`TT.UTIL` is small but semantically nasty — it is the first package in the whole migration
where Oracle's COMMIT and `PRAGMA AUTONOMOUS_TRANSACTION` collide with PostgreSQL's
FUNCTION/PROCEDURE rules. It is deliberately in this plan so that collision surfaces early
and cheaply.

Output: three specs, three pgTAP suites, two expected-output suites. **All red.**
</objective>

<the_one_rule>
**Do not read `pg_migration/output/` and do not read any file under `migration/pgsql/`
other than the plog stub's FINDINGS.md.**

The specs and tests in this plan are derived from `ddl/src/**` and from nothing else. The
translations of these packages do not exist yet — that is on purpose, and it is the whole
structural defence of this phase. A test written by looking at a translation proves only
that the translation does what the translation does. `provenance_lint.sh` will check this
against git history, but the honesty has to happen here, at authoring time.

If you find yourself wanting to know "what would be easy to implement in PL/pgSQL" — stop.
That is the wrong question. The only question is "what does the Oracle code do".
</the_one_rule>

    Every clause carries a `ddl/src/...:LINE` citation. The five checklist dimensions get
    real answers, not ceremony. Specifically:

    - **SELECT INTO strictness.** DBPROP has 2 sites and exactly 1 NO_DATA_FOUND handler;
      OSAG_AUTH has 6 sites and 1 NO_DATA_FOUND handler. So MOST of these sites have NO
      handler. Read each one and decide, per site, what Oracle would do on zero rows: raise
      NO_DATA_FOUND and propagate it to the caller. That is behaviour, not an accident, and
      the PL/pgSQL translation must reproduce it (STRICT, unhandled) rather than silently
      returning NULL. Where the Oracle code DID handle NO_DATA_FOUND, record what it did —
      `auth_osag_auth.sql` has the documented case where a missing profile means "nothing to
      do". Number every site by line so the translation plan cannot miss one.
    - **Empty-string / NULL.** `get_string_by_host(i_host_id NUMBER, i_property_name VARCHAR2)`
      takes a string parameter that is compared. Under Oracle, a caller passing `''` and a
      caller passing NULL are indistinguishable; under PostgreSQL they are not. State what
      the translation must do at the boundary and what a test must assert.
    - **Exception codes.** Record every handler and every re-raise with its Oracle line.
      Mark the Oracle→SQLSTATE mapping PROVISIONAL — XCUT-01 (Phase 3) owns the authoritative
      table; the spec records the requirement, it does not invent the answer.
    - **Package state.** Both have zero package-body state per the inventory. Confirm it by
      reading, and say so — "verified none, by reading lines N..M" is a real answer;
      "N/A" is not.
    - **FUNCTION vs PROCEDURE.** Neither COMMITs. Both map straightforwardly. Say so and move on.

    In `## Assumptions / Unresolved`, be blunt about anything the source does not settle —
    e.g. whether a `%TYPE` anchor resolves to a column that the migrated schema actually has,
    or whether an implicit NUMBER↔VARCHAR2 coercion Oracle would perform silently has a
    PostgreSQL equivalent. There is no live Oracle. An honest "unresolved" here is a Phase 4
    input; a confident guess here is a Phase 4 bug.

    Run `python3 migration/spec/spec_lint.py` until clean.

  </read_first>
  <action>
    Write `migration/spec/tt.util.md` (clause_prefix `UTIL`) covering all 5 public routines.

    The FUNCTION-vs-PROCEDURE dimension is the point of this spec. Be precise:
      - Oracle declares all 5 as PROCEDURE, and `name-map.csv` carries `pg_kind=procedure`.
        That looks settled. It is not, and here is why it matters: a PostgreSQL PROCEDURE
        that issues COMMIT cannot be CALLed from inside a FUNCTION body. So the question is
        not "what kind is UTIL" but "**what kind is every caller of UTIL, transitively**".
      - `TT.UTIL` is inside the four-package TT cycle group (`EVENT_INTERFACE`,
        `OSAG_NOTIFY`, `TICKET_INTERFACE`, `UTIL` — see `migration/analyze/known_cycles.json`).
        Its callers are `EVENT_INTERFACE` and `TICKET_INTERFACE`. Record which specific
        routines call it, and whether any of them is an Oracle FUNCTION. If one is, that is a
        hard PostgreSQL constraint that propagates up the call chain, and it must be written
        down here in bold as an input to XCUT-04.
      - `close_old_dev_tickets` carries `PRAGMA AUTONOMOUS_TRANSACTION`. PostgreSQL has no
        equivalent. PITFALLS.md names this as one of exactly two table-writing autonomous
        sites in the entire corpus and assigns the decision to Phase 3 (XCUT-05). **Do not
        decide it here.** Spec what Oracle DOES (the write survives a caller's rollback),
        state the three candidate PostgreSQL behaviours, and record in
        `## Assumptions / Unresolved` that Phase 2 will translate it as a plain PROCEDURE
        with COMMIT — accepting a semantic delta — and that the pilot's tests therefore do
        NOT assert rollback-survival for it. Naming the delta is the deliverable; hiding it
        would be the failure.
      - The COMMITs at 234/244: which routine are they in, what do they commit, and what
        does a caller see after them? After a COMMIT inside a PostgreSQL procedure, execution
        continues in a NEW transaction — anything the caller assumed was still locked or
        visible from before is gone. Record the consequence.

    SELECT INTO: 3 sites, ZERO exception handlers in the whole package. That means every one
    of them propagates NO_DATA_FOUND to the caller if it finds nothing. Spec that explicitly
    per site — it is the difference between STRICT (correct) and a silent NULL (wrong).

    Run `spec_lint.py` until clean.
  </action>
