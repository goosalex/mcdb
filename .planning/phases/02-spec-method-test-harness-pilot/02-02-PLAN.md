<design_decisions>
- **D-P2 — Spec path and clause IDs.** One spec per Oracle package at
  `migration/spec/<pg_schema>.<oracle_package_lower>.md`, e.g. `migration/spec/tt.ticket_interface.md`.
  Every behavioural claim is a numbered CLAUSE with a stable ID `S-<PREFIX>-NNN`
  (e.g. `S-TICKET-014`). Clause IDs are what tests cite. They never get renumbered.
- **D-P4 — Anti-circularity is enforced by execution ORDER, not by good intentions.**
  In this phase, the plan that writes a package's spec and tests runs BEFORE the plan that
  writes its translation, so the test author's context provably cannot contain the
  translation — it does not exist yet. `provenance_lint.sh` turns that into a permanent,
  re-checkable property of git history.
</design_decisions>

  <action>
    Write `migration/spec/CHECKLIST.md` — the five dimensions SPEC-03 mandates, each with
    a precise, answerable question and the Oracle-source evidence that answers it. These
    are not vibes; each maps to a documented pitfall:
      1. **Empty-string / NULL handling** (Pitfall 2) — for every VARCHAR2 parameter,
         column, and local that takes part in an IS NULL check, an equality/inequality
         comparison, or concatenation: what did Oracle do when it was `''`? Oracle collapses
         `''` to NULL; PostgreSQL does not. Record the per-parameter decision.
      2. **SELECT INTO strictness** (Pitfall 1) — for EVERY `SELECT ... INTO` site (the
         inventory gives you the line numbers): is zero-rows possible, is multi-rows
         possible, and what did the Oracle handler do? Oracle raises NO_DATA_FOUND /
         TOO_MANY_ROWS by default; PL/pgSQL without STRICT raises neither. Every site gets
         an explicit STRICT / no-STRICT decision with a reason.
      3. **Exception codes** (Pitfall 3) — every RAISE_APPLICATION_ERROR code, every
         handled Oracle exception, every bare re-raise. Record the Oracle code and the
         intended PostgreSQL SQLSTATE. The authoritative code map is Phase 3 (XCUT-01);
         the pilot records what it needs and marks the mapping PROVISIONAL.
      4. **Package state** (Pitfall 5) — any package-body-level variable that is not a
         CONSTANT, and any trailing unnamed initialisation block. `package_in_name`
         flattening silently discards both.
      5. **FUNCTION vs PROCEDURE** (Pitfall 6) — does the routine COMMIT or ROLLBACK, does
         it carry an autonomous-transaction pragma, and is it called from inside anything
         that must be a FUNCTION? A PostgreSQL FUNCTION can never COMMIT. Note that
         `pg_kind` in `name-map.csv` is PROVISIONAL and the final call belongs to Phase 3
         (XCUT-04) — the spec records the finding and its consequences, it does not pretend
         to settle it.

    Write `migration/spec/TEMPLATE.md` — the exact skeleton every spec must fill:
      - YAML front-matter: `oracle_schema`, `oracle_package`, `pg_schema`, `pg_prefix`,
        `clause_prefix`, `oracle_spec` (path), `oracle_body` (path), `public_routines` (int).
      - `## Routines` — one subsection per public routine, with its Oracle signature and
        the PostgreSQL object name COPIED FROM `name-map.csv` (never re-derived).
      - `## Clauses` — the numbered behavioural claims. Each clause is a table row or block
        with: ID, `routines:` (which routines it constrains), the claim in one sentence,
        and `source:` — one or more `ddl/src/...:LINE` citations. **A clause with no Oracle
        source citation is not a clause; it is a guess.**
      - `## Checklist` — the five headings from CHECKLIST.md, each answered for THIS package.
      - `## Assumptions / Unresolved` (SPEC-02) — what static analysis could not settle,
        and why. There is no live Oracle to fall back on. This section must never be empty:
        if nothing is unresolved, it says so explicitly and states what was checked to reach
        that conclusion. An honest "I cannot know this from the source" here is worth more
        than a confident guess, because a guess here silently poisons Phase 4.

    Write `migration/spec/README.md` — how to author a spec, the three linters and what
    each rejects, and the standing rule: **the spec is derived from `ddl/src/**` and from
    nothing else.** Not from `pg_migration/output/` (untrusted ora2pg), not from the
    PL/pgSQL translation (which does not exist yet), not from what would be convenient to
    implement.
  </action>

    Write `migration/spec/trace_lint.py` — the HARN-05 gate. Every test must be traceable
    to an Oracle-derived spec clause.
      - For pgTAP files (`migration/test/pgtap/*.sql`): every assertion's DESCRIPTION string
        must begin with a clause ID, i.e. match `^S-[A-Z0-9]+-\d{3}: `. Parse the
        description literals out of the assertion calls. Then resolve each cited ID against
        the spec for that file's package (derived from the filename convention). Fail on:
        a description with no clause ID; a cited ID that does not exist in the spec; a test
        file for a package with no spec at all.
      - For expected-output files (`migration/test/regress/sql/*.sql`): the file must carry
        a header line `-- verifies: S-XXX-001, S-XXX-014` naming at least one clause, and
        every ID listed must resolve.
      - Emit a coverage report: which clauses of each spec have at least one test citing
        them. This is a REPORT, not a gate — Phase 2 does not require a test per routine
        (VER-02 belongs to Phase 4). But the number must be visible so nobody mistakes the
        pilot for coverage.
      - The `_canary` package from plan 02-01 is exempt (it tests the harness, not a
        translation); exempt it explicitly by name rather than by a loose pattern.

    Write `migration/spec/provenance_lint.sh` — the structural anti-circularity gate.
    For each translated package file under `migration/pgsql/<schema>/<pkg>.sql`, find:
      - `SPEC_ADD` = the commit that first added `migration/spec/<schema>.<pkg>.md`
        (`git log --diff-filter=A --format=%H -- <path> | tail -1`)
      - `TEST_ADD` = the commit that first added that package's first test file
      - `TRANS_ADD` = the commit that first added the translation file
    and assert `git merge-base --is-ancestor $SPEC_ADD $TRANS_ADD` AND
    `git merge-base --is-ancestor $TEST_ADD $TRANS_ADD`. Both must hold. If either fails,
    exit non-zero with:
      `<pkg>: translation predates its spec/tests — the tests may have been written from the
       translation, which proves nothing.`
    Also assert the translation's commits never MODIFIED a test file for that package:
    for every commit touching the translation file, `git show --name-only` must not also
    touch `migration/test/{pgtap,regress}/<schema>__<pkg>__*`. If a test genuinely must
    change after translation, the escape hatch is explicit and leaves evidence: amend the
    SPEC first (citing Oracle source), then change the test in a commit that does not touch
    the translation, and log it in `migration/spec/TEST-AMENDMENTS.md` with the reason.
    The linter reads that ledger and permits exactly the amendments it lists.

    Both linters must be runnable before any spec or translation exists (they should report
    "0 specs, 0 translations, nothing to check" and exit 0) — plans 02-04..02-12 will call
    them as they go.
  </action>
  <verify>
    <automated>bash -c 'set -e; python3 migration/spec/trace_lint.py; bash migration/spec/provenance_lint.sh; echo LINTERS_RUN_CLEAN_ON_EMPTY_TREE'</automated>

  </verify>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Oracle source (`ddl/src/**`) → spec | The ONLY sanctioned input to a spec. Any other input is a correctness breach |
| spec → test → translation | The verification chain. Reversing any arrow makes the whole chain vacuous |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-05 | Repudiation | spec clause with no Oracle citation | critical | mitigate | `spec_lint.py` requires a `ddl/src/...:LINE` citation per clause AND verifies the line exists in that file — a fabricated citation is caught |
| T-02-06 | Spoofing | a test written from the translation, masquerading as spec-derived | critical | mitigate | `provenance_lint.sh` git-ancestry assertion: the translation cannot predate its spec/tests, and a translation commit may not edit tests |
| T-02-07 | Information Disclosure | spec quietly drops routines it found hard | high | mitigate | `spec_lint.py` routine-coverage check against `inventory.json` — the 38 TICKET_INTERFACE routines cannot be silently subsetted |
| T-02-08 | Tampering | linters relaxed later to make a red build green | medium | mitigate | Linter behaviour is pinned by the `migration/spec/tests/` unit suite and by the bad-fixture rejections; weakening a rule breaks a test |
</threat_model>
