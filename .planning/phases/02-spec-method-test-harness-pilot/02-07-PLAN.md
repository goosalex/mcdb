intended. **Spec them as two distinct routines with distinct signatures.** Collapsing them into
one clause would lose a routine, and `spec_lint.py`'s coverage check counts the pair once, so
it would NOT catch you. This is the one place in this spec where the linter cannot save you.

    Three of these deserve extra care:

    - **`get_next_recent_ticket` and `replace_id_placeholders` are the only two FUNCTIONs.**
      A PostgreSQL FUNCTION can never COMMIT, and cannot CALL a procedure that does. Trace
      what each calls, transitively. `TT.UTIL` is in the same cycle group and DOES commit
      (lines 234/244). If either FUNCTION reaches a committing routine, that is a **hard
      PostgreSQL error**, not a preference — and it means the FUNCTION must become a PROCEDURE
      with an OUT parameter, which changes every call site including client code. Pitfall 6
      calls this out as the one whose late discovery is expensive. Put the finding in the spec
      in bold, mark it an XCUT-04 input, and — critically — do not quietly "solve" it by
      choosing a translation shape. Phase 3 decides. Phase 2 finds and reports.

    - **`merge_tickets`** touches two tickets and their dependents. Spec the ordering and what
      happens to the loser's children, precisely. This is where a subtly wrong translation
      destroys data rather than throwing an error.

    - **`deleteTicket`** — spec exactly what cascades and what does not. Same reason.

    Then complete `## Checklist` for the whole package:
      - **Empty-string / NULL**: `change_subject`, `change_summary`, `change_label`,
        `change_customer_reference`, `change_partner_reference` all take VARCHAR2 text.
        Under Oracle, clearing a field by passing `''` and clearing it by passing NULL are the
        same operation. Under PostgreSQL they are not — `''` is a real zero-length string that
        satisfies NOT NULL. Enumerate every affected parameter and state what the translation
        must do at the boundary. This is the most likely place in the entire pilot for a silent
        data-semantics regression.
      - **Exception codes**: the 13 NO_DATA_FOUND and 10 OTHERS handlers, each cited.
      - **Package state**: none per the inventory — confirm by reading and say how.
      - **FUNCTION vs PROCEDURE**: the finding above.
    And `## Assumptions / Unresolved`: what 2,484 lines of source genuinely does not settle.

    Also add a clause for the **mutual recursion with `TT.EVENT_INTERFACE`**: which routines

    CREATE time, so the two translations can load in any order; only execution needs both.

    Run `spec_lint.py` — its routine-coverage check against `inventory.json` is what proves all
    38 are present.
