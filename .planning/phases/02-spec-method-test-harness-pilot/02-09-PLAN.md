<the_rules_for_translation_plans>
These apply to every translation plan in this phase (02-09 through 02-12).

1. **You may not modify any file under `migration/test/`.** `provenance_lint.sh` checks this
   against git history and will fail the phase if you do. If a test is genuinely wrong, the
   escape hatch is explicit and leaves evidence: amend the SPEC first, citing `ddl/src/...:LINE`;
   commit that separately; log it in `migration/spec/TEST-AMENDMENTS.md` with the reason; then a
   test change may follow in its own commit. Do not silently bend a test to fit your code — that
   converts a real finding into a green build and is the exact failure this phase exists to
   prevent.

2. **Do not use `pg_migration/output/` as your starting point.** Not as a base to edit, not as a
   reference to "check against". PITFALLS.md Pitfall 7 documents concrete, confirmed
   mistranslations in that tree, and the tell that you have leaned on it is a translation that
   mirrors ora2pg's line-by-line structure rather than the Oracle source's actual control flow.
   You may consult it as a CHECKLIST of Oracle-vendor call sites it noticed — nothing more.

3. **Object names come from `migration/mapping/name-map.csv`.** Verbatim. Do not re-derive, do
   not "improve", do not shorten. Phase 5's client regexp kit is generated from that file; a name
   you invent here is a client call site that silently never gets rewritten.

4. **Every `SELECT INTO` gets the verdict its spec assigned.** Not STRICT everywhere. Not STRICT
   nowhere. The per-site verdict, site by site. PITFALLS.md is explicit that both blanket passes
   are wrong.

5. **No Oracle vendor-package identifiers survive into the output.** The acceptance criteria grep
   for them.
</the_rules_for_translation_plans>

      - **Which of `TT.UTIL`'s callers can survive it being a COMMIT-bearing PROCEDURE?** A
        PostgreSQL PROCEDURE that COMMITs cannot be CALLed from inside a FUNCTION body. `TT.UTIL`
        is called by `TT.EVENT_INTERFACE` and `TT.TICKET_INTERFACE`. `TT.TICKET_INTERFACE` has two
        FUNCTIONs (`get_next_recent_ticket`, `replace_id_placeholders`) and
        `TT.EVENT_INTERFACE` has one (`ticket_type_for_event_type`). **If any of those three
        FUNCTIONs transitively reaches a `TT.UTIL` COMMIT, that is a hard PostgreSQL runtime
        error and the FUNCTION cannot stay a FUNCTION.** Trace it and state the answer plainly,
        with call-chain evidence. If it holds, name the routines that must change shape and note
        that their call sites — including client Perl/Java — change shape too, which makes this a
        Phase 5 client-regexp input as well.
