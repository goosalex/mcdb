<objective>
Stand up the dual test harness and the one-command runner, on the local PostgreSQL 17.10
instance, and prove both halves can genuinely fail.

Purpose: Every later plan in this phase runs its work through this harness. If the harness
cannot fail, every green result it ever reports is worthless — so the deliverable is not
"a harness exists" but "a harness that was observed rejecting a wrong answer".

Output: `migration/test/` — a runnable harness (pgTAP via pg_prove + plain-SQL
expected-output diffing), a one-command runner reporting per-package pass/fail, a
disposable-database bootstrap, and the `redgreen.sh` gate script that later plans invoke.
</objective>

<design_decisions>
Stated plainly so later plans do not re-litigate them. All are reversible.

- **D-P1 — The harness lives in `migration/test/`.** Under `migration/` (the trusted,
  generated-artifact tree from Phase 1), NOT under `pg_migration/` (untrusted ora2pg
  output) and NOT under `tests/` (the pre-existing Java/Testcontainers ORM harness, which
  is unrelated and must not be disturbed).
- **D-P8 — Isolation via template database.** `bootstrap.sh --db NAME` creates a fresh
  database. Once plan 02-03 has built the template `mcdb_tmpl` (schema + fixtures),
  `bootstrap.sh` uses `CREATE DATABASE NAME TEMPLATE mcdb_tmpl`, which is near-instant.
  This is what lets four spec/test plans (and later four translation plans) run in the
  same wave without racing each other in one shared database.
- **D-P9 — Package identity comes from `migration/mapping/name-map.csv`.** Test files are
  named `<pg_schema>__<oracle_package_lower>__<topic>.sql`. The runner parses the package
  from the filename and REJECTS any file whose `(pg_schema, oracle_package)` pair is not a
  real pair in the name map. This is what makes Phase 1's SSOT load-bearing rather than
  decorative.
</design_decisions>

  <name>Task 2: Both harness halves + the one-command runner with per-package pass/fail</name>
  <files>migration/test/run-tests.sh, migration/test/lib/pkgname.py, migration/test/pgtap/_canary__canary__smoke.sql, migration/test/regress/sql/_canary__canary__smoke.sql, migration/test/regress/expected/_canary__canary__smoke.out</files>

  </read_first>
  <action>
    Write `migration/test/lib/pkgname.py` (Python 3.12 stdlib only, matching Phase 1's D-B).
    It exposes the package-identity resolution the runner depends on:
      - Load `migration/mapping/name-map.csv` into the set of valid `(pg_schema,
        oracle_package_lower)` pairs.
      - `parse(filename) -> (pg_schema, oracle_package_lower, topic)` for the naming
        convention `<pg_schema>__<oracle_package_lower>__<topic>.sql`.
      - `validate(paths) -> errors[]`: any test file whose parsed pair is NOT in the name
        map is an ERROR (exit non-zero), except the reserved literal `_canary` schema which
        is allowed for harness self-tests only.
      - A `--list` CLI mode printing the discovered `(package, file)` pairs, so the runner
        can consume it with no CSV parsing of its own.
    This is the enforcement point for D-P9: nobody invents a package name outside the SSOT.

    Write `migration/test/run-tests.sh` — the one command (HARN-04):
      `run-tests.sh [--db NAME] [--install DIR] [--package PKG] [--filter GLOB]`
      1. Default `--db mcdb_test`. If the database does not exist, call `bootstrap.sh`.
      2. If `--install DIR` is given, load every `*.sql` under DIR into the database with
         `ON_ERROR_STOP=on`, sorted by path (deterministic). A load failure aborts with a
         non-zero exit and prints the offending file. This is how translated PL/pgSQL gets
         into the database in later plans; PL/pgSQL bodies are not resolved at CREATE time,
         so forward references inside the TT cycle group load fine in any order.
      3. Run `pkgname.py --list` over `pgtap/*.sql` and `regress/sql/*.sql`; abort on any
         validation error.
      4. **pgTAP half (HARN-01):** run `pg_prove --ext .sql -d NAME --verbose` per package's
         files, capturing the TAP stream. Record tests-passed/tests-planned per package.
      5. **Expected-output half (HARN-02):** for each `regress/sql/X.sql`, run
         `psql -X -q -v ON_ERROR_STOP=0 -f regress/sql/X.sql > regress/results/X.out 2>&1`,
         then `diff -u regress/expected/X.out regress/results/X.out`. Non-empty diff = FAIL
         for that file; print the diff. Use `-v ON_ERROR_STOP=0` deliberately here: an
         expected-output test is allowed to provoke an error and assert on the error text,
         which is exactly how exception-code expectations get pinned.
      6. Print an aggregate table, one row per Oracle package:
         `PACKAGE | PGTAP (pass/total) | REGRESS (pass/total) | RESULT`
         followed by `TOTAL: N packages, P pass, F fail`.
      7. Exit 0 only if every package passed and at least one test ran. **Zero tests
         discovered must exit non-zero** — an empty suite silently "passing" is the exact
         failure this phase exists to prevent.
      `set -euo pipefail` throughout.

    Write the canary self-test, in BOTH harnesses, under the reserved `_canary` name:
      - `pgtap/_canary__canary__smoke.sql`: a pgTAP script with `plan(2)`, one `ok(true,...)`
        and one assertion over a trivially-known value.
      - `regress/sql/_canary__canary__smoke.sql` plus its golden
        `regress/expected/_canary__canary__smoke.out`.
    The canary exists so Task 3 can break it on purpose.
  </action>

  </verify>
  <done>
    `run-tests.sh` runs both harnesses against a bootstrapped database in one invocation,
    prints a per-package pass/fail table, and exits 0 on the green canary. A test file

      (b) Corrupt one byte of the canary's golden `.out` file. Run `run-tests.sh`. It MUST

    Record both observed exit codes and the failing output in the plan SUMMARY. If either
    mutation still exits 0, the harness is broken — fix it before proceeding, because
    everything downstream in this phase is worthless without this property.

    Then write `migration/test/redgreen.sh` — the mechanised form of Phase 2's success
    criterion 5, so red-before/green-after is a repeatable gate rather than a one-time
    anecdote:
      `redgreen.sh --db NAME --install DIR [--package PKG]`
      1. RED: build a fresh database from the template WITHOUT installing DIR, then run
         `run-tests.sh --db NAME` restricted to the packages present in DIR. It MUST exit
         non-zero (the translated objects do not exist, so every assertion against them
         errors). If it exits 0, ABORT with
         `RED PHASE DID NOT FAIL — the tests do not actually exercise the translation`.
         Capture the output to `redgreen-red.log`.
      2. GREEN: rebuild the database from the template, install DIR, re-run. It MUST exit
         zero. Capture to `redgreen-green.log`.
      3. Print `RED->GREEN PROVEN for: <packages>` and exit 0 only if both phases behaved
         as required.
    An abort in step 1 is the single most valuable thing this script does: it catches a
    test suite that would pass even against a nonexistent implementation.

    Write `migration/test/README.md`: the layout, the three commands (`bootstrap.sh`,
    `run-tests.sh`, `redgreen.sh`), the file-naming convention, the D-P8/D-P9 decisions,
    and the standing rule that a green suite that was never seen red proves nothing.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| shell → `sudo apt` / `sudo -u postgres` | The harness escalates privilege to install packages and to reach the DB via peer auth |
| test files → test database | Arbitrary SQL from `migration/test/**` executes with superuser rights |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | `bootstrap.sh` DROP DATABASE | high | mitigate | Refuse to operate on any database name not matching `^mcdb_(test\|tmpl\|harness)[a-z0-9_]*$`; hard-fail otherwise. A typo must never drop a real database |
| T-02-02 | Elevation of Privilege | tests run as `postgres` superuser | medium | accept | The test instance is a local, disposable, developer-only PostgreSQL. Rationale recorded; Phase 5's container is where a non-superuser role gets pinned |
| T-02-03 | Denial of Service | `pg_terminate_backend` in bootstrap | low | accept | Scoped by the same database-name allowlist as T-02-01, so it cannot terminate backends on an unrelated database |
| T-02-04 | Tampering | apt package provenance | low | accept | PGDG apt repository, user-approved packages, distro-signed. Not an npm/pip/cargo ecosystem — no slopcheck gate applies |
</threat_model>
