<objective>
Spec `TT.EVENT_INTERFACE` from Oracle source and write its tests — before its translation
exists.

Purpose: This is the package the roadmap named as Phase 2's research risk, in as many words:
*"dynamic SQL (DBMS_SQL, EXECUTE IMMEDIATE) in pilot packages may resist static spec
derivation and require manual tracing; no live-Oracle baseline is available to fall back on."*
`TT.EVENT_INTERFACE` is the pilot's only `static_resolution: incomplete` node — genuine
dynamic SQL at `ddl/src/pkgb/tt_event_interface.sql:971`.

The deliverable here is therefore NOT a confident spec. It is an HONEST one. The failure
mode this plan exists to prevent is a plausible-looking guess about what the dynamic SQL does,
recorded as fact, which then silently poisons Phase 4 — where it will be far more expensive
to find. An explicit "static analysis cannot settle this; here is what we know, here is what
we do not, here is what would settle it" is a better artifact than a confident fiction.

Output: one spec, one dynamic-SQL trace document, one pgTAP suite, one expected-output suite.
**All red.**
</objective>

<known_ground_truth>
From Phase 1's `inventory.json` and `depgraph.json`, verified during planning:

- **8 public routines**: `newevent_new`, `addevent_new`, `moveevent`,
  `ticket_type_for_event_type` (FUNCTION — the only one), `exec_event_type_actions`,
  `add_history_event`, `demote_event`, `promote_event`. **1 private**: `is_esc_supp_active`.
- **34 SELECT INTO sites**: 79, 94, 104, 118, 157, 165, 176, 203, 344, 377, 384, 389, 423,
  561, 566, … (the full array is in `inventory.json`).
- **Handlers: 5 NO_DATA_FOUND, 0 TOO_MANY_ROWS, 6 OTHERS.**
- **`static_resolution: incomplete`**, with exactly one reason:
  `{"construct": "EXECUTE IMMEDIATE", "line": 971}`. **One site. Not a swarm.** That is good
  news and it means a careful manual trace is genuinely tractable.
- No COMMIT, no ROLLBACK, no autonomous transaction, no package state.
- Size: spec 155 lines, body **1172 lines**.
- Calls out to: `MSS.OSAG_DBPROP`, `OSAG_PLOG`, `TT.OSAG_NOTIFY`, `TT.TICKET_INTERFACE`, `TT.UTIL`.
- **Mutually recursive with `TT.TICKET_INTERFACE`** — an accepted cycle group. Neither can
  precede the other.

`migration/README.md` carries a standing warning that some `incomplete` flags are lexer false
positives (e.g. `INSERT INTO schema.table (col_list)` misread as a call). This one is not:
`EXECUTE IMMEDIATE` at a specific line is a real construct. Confirm it by reading line 971,
then trace it.
</known_ground_truth>

    Trace the dynamic SQL at `ddl/src/pkgb/tt_event_interface.sql:971` by hand and write
    `migration/spec/DYNAMIC-SQL-TRACE.md`. Structure it so Phase 4 can reuse it — there are
    ~12 more dynamic-SQL sites in the corpus and this is the first, so the FORM of this
    document matters as much as its content.

    For the site, record:
      - The exact Oracle source lines (quote them, with line numbers).
      - **What builds the statement string.** Follow every variable that feeds it back to its
        origin. Is it a literal? A concatenation of literals? A concatenation involving a
        parameter or a column value? This is the crux: if any user- or data-controlled value
        reaches the statement text, the translation must use `format()` with `%I`/`%L`
        quoting, not string concatenation — otherwise the migration ports a SQL-injection
        vector into PostgreSQL along with the logic.
      - **The set of statements it can actually produce.** If the possible statements are
        enumerable from the source (a common Oracle idiom is dynamic SQL over a table name
        chosen from a fixed list), enumerate them — and then say plainly that the translation
        should replace the dynamic construction with static SQL, because the dynamism was
        never needed.
      - **What it calls.** This is why the node is flagged: the depgraph could not see the
        call edge. Name the callee if the trace reveals it, and note that the depgraph's edge
        list for this node is therefore incomplete by exactly this much.
      - **What you cannot determine from source alone**, and what WOULD determine it (an
        Oracle 19c container running the code — deferred to v2 as ORA-01, per
        `.planning/REQUIREMENTS.md`).

    Then a `## Recommendation` for the translation, one of:
      - `STATIC` — the dynamism is spurious; the statement set is enumerable; translate to
        plain SQL and record the enumeration.
      - `EXECUTE format()` — genuinely dynamic; identifier/literal quoting specified exactly.
      - `UNRESOLVED — DO NOT GUESS` — the source does not determine the behaviour. If this is
        the verdict, say so, and the pilot translates the site as a routine that RAISES a
        clearly-labelled "not yet translated: needs Oracle baseline" exception rather than
        shipping a guess. A loud failure is a correct outcome here; a quiet wrong answer is not.

    That third option must be genuinely available to you. Do not talk yourself into a
    recommendation you cannot defend from the source.
  </action>
