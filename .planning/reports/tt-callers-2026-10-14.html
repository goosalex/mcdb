Packages that call into TT — procedures and read / write classification

Generated 2026-10-14 from migration/analyze/depgraph.json (call edges), the Oracle package bodies under ddl/src/pkgb/ (statement-level scan of every tt. reference), ddl/generated/grants/ and the view definitions in ddl/export/. "TT" means the ticketing schema: packages TICKET_INTERFACE, EVENT_INTERFACE, OSAG_NOTIFY, UTIL, ESCALATION_INTERFACE and the 34 TT tables.

9packages outside TT that reference TT objects
6of them call TT package routines (16 call sites)
3touch TT tables with direct SQL only (all read)
9distinct TT routines called from outside; 8 of them modify data
13views in other schemas read TT tables

How the classification works

  • Package call: the caller invokes a TT package routine. The access class is that of the TT routine, computed from its Oracle body: WRITE if it, or any TT routine it calls transitively, runs INSERT / UPDATE / DELETE / MERGE or pulls a sequence; read otherwise.
  • Direct SQL: the caller's own statement names a TT table. Classified by the statement verb. %TYPE anchors on TT columns are ignored (compile-time only).
  • Every call from outside is schema-qualified (tt.<package>.<routine>); no caller uses a public synonym for a TT package. No trigger, standalone procedure, materialized view or scheduler job outside TT references TT.

Reading the table. Six packages change TT data, all through the TT packages, never by direct DML. MC.MONITORING_TICKET_PROCESSES and NIDS.OSAG_NIDS are the heaviest integrators: they open tickets, attach events and change status. The three read-only packages all use the same five-table join over tt.ticket / service_window / host2service_window / maintenance_window / cust_maintenance_window to decide whether a host is inside a maintenance window. That join is copy-pasted in MC.MONITORING (1×), MC.OSAG_MAINTSYNC (4×) and NIDS.OSAG_NIDS (2×) and is a candidate for one shared view in PostgreSQL.

7. Consequences for the migration

  1. Wave order holds. All six calling packages are in waves 4–5, after the TT cycle group (wave 3). TICKETEVOLUTION.CALCULATOR (wave 1) and MC.OSAG_MAINTSYNC (wave 2) only read TT tables, which exist from the schema load, so their early placement is correct.
  2. 9 external entry points carry the integration risk: addevent_new, change_status, change_subject, clear_customer_escalation, delete_notifications_for_login, exec_event_type_actions, newevent_new, newticket_new, ticket_type_for_event_type. Their signatures (including the many defaulted parameters of newevent_new) are what the client regexp list must rewrite to tt.event_interface_newevent_new(...) etc.
  3. ESCALATION_INTERFACE must be translated before any wave-4 caller is tested, otherwise every newevent_new / addevent_new path that has an event action configured fails at the dynamic dispatch.
  4. FUNCTION-vs-PROCEDURE matters for one call. NIDS.OSAG_NIDS uses ticket_type_for_event_type as a FUNCTION inside an assignment; it has no DB access, so no COMMIT collision (consistent with the XCUT-04 finding). All other calls are PROCEDURE calls in statement position.
  5. Direct-DML accounts (SVC_API_TICKETING, MCA, SVC_MC_PORTAL, DECOMM, MCMGW, SVC_AUTOMATION_EXECUTOR, PERLTICKET, WEBSW, SVC_CONIFER) write TT tables without going through the packages. Their behaviour is outside the PL/SQL translation but must be preserved in the PostgreSQL grant set, and the two TT triggers (TICKET_UPDATE_TRG, TODO_ITEM_UPDATE_TRG) are the only server-side logic that still runs for those writes.
