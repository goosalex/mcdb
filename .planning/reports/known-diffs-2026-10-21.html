The four documented Oracle vs PostgreSQL differences

MCDB migration, TT closure. Live differential run against the Oracle Free 23.7 container mcdb-ora and the PostgreSQL container mcdb-pg, 2026-10-21. Branch phoenix/tt_container_ora.

What this report covers. The differential harness (migration/test/diff) runs the same scenario script on both databases and compares the resulting rows. Of the 25 scenarios, every difference was either fixed in the translation or turned out to be one of the four behaviours below. These four are not fixed in the translated code. They are frozen as expected differences (known.diff files), so the comparison stays green while still failing loudly if the behaviour drifts. Each needs a human decision, listed in the last section.

1. Earlier writes survive a caught error on Oracle, not on PostgreSQL

Where it shows. TT.ESCALATION_INTERFACE.escalate_os and escalate_customer called on a ticket that is already closed (status 102). Scenario tt__escalation_interface__closed_ticket.

What happens. Both routines first update the ticket (escalation status becomes 10, the escalation date is stamped) and only then try to add an event. Adding an event to a closed ticket fails with the "ticket closed" error. Neither routine catches it, so the error reaches the caller. Both databases raise the same error code. The difference is what remains in the ticket row once the caller catches the error and carries on, as the monitoring jobs in MC do.

Oracle Undoes only the single statement that failed. The update that ran before it stays. The ticket ends with escalation status 10 and a set escalation date.
PostgreSQL A caught error undoes everything the failed call did (the exception block is a sub-transaction). The ticket is back to escalation status 0 and no date.

Why it is not fixed in the translation. This is how each engine handles a caught error. To make PostgreSQL keep the update, the translation would have to commit it separately (an autonomous transaction, which PostgreSQL does not have) or restructure the routine so the update happens after the event is added, which changes the order Oracle users see. The spec records this under XCUT-05 and notes that the PostgreSQL outcome is arguably the saner one: a ticket should not be marked "escalated" if the escalation event was never written.

Scope. Only static calls are affected. When the same routine is reached through exec_event_type_actions (dynamic dispatch, case 3), Oracle also undoes the whole call, so both engines agree there. Confirmed live in scenario tt__event_interface__exec_actions, step 09.

2. Email fails on Oracle inside the container, PostgreSQL queues it

Where it shows. TT.OSAG_NOTIFY.send_test_notification for the EMAIL notification type. Scenario tt__osag_notify__send_test, steps 02 and 03.

What happens. On Oracle, sending mail goes through the built-in UTL_SMTP package, which opens a network connection to a mail server. The test container has no mail server and no network permission for the TT user, so Oracle raises ORA-24247 ("network access denied by access control list"). send_mail logs that and re-raises, and send_test_notification has no handler, so the caller sees the error. The SMS variant swallows the error and reports success.

PostgreSQL has no built-in mail client at all. The translated OSAG.OSAG_MSG therefore writes the message into the table osag.msg_outbox and returns normally. Something outside the database has to pick the rows up and send them.

State of one test message

Why it is not fixed in the translation. Two separate causes stack here. First, the Oracle error is an artefact of the test container: production Oracle has a mail relay and the network permission, so the step would succeed there. Second, the outbox is a deliberate platform decision (spec S-MSG-013, deviation class PLATFORM): PostgreSQL cannot speak SMTP from inside a transaction, and an outbox also survives rollbacks correctly. The visible contract changes slightly: send_test_notification can no longer fail because of mail delivery.

3. The translation refuses configured procedures that Oracle would run

Where it shows. TT.EVENT_INTERFACE.exec_event_type_actions. Scenario tt__event_interface__exec_actions, step 05.

What happens. When an event arrives, this routine looks up the event type in the configuration table tt.event_action, reads a procedure name from it, and runs that procedure with the event id. It is the only place in the whole code base where SQL is assembled and executed at run time. On Oracle, any name in that column is executed. In the translation I put a safety list in front of the call: only the four known escalation procedures may run, anything else raises a clear error instead of executing. The test configured a real but unlisted procedure, clear_customer_escalation. Oracle ran it and reset the ticket's escalation status from 20 to 0. PostgreSQL refused and left the ticket at 20.

Why it is not fixed in the translation. This difference is intentional hardening. Reproducing Oracle exactly would mean executing any string found in a configuration table. The list currently contains the procedures that the master data and the spec name. If the production tt.event_action rows name anything else, the translation would start raising P0001 for those event types in production, so the list must be checked against production configuration before go-live.

4. The "recoverable status" is wiped for tickets without a public event

Where it shows. TT.TICKET_INTERFACE.change_status, change_status_event_id_out and expire_status. Scenario tt__ticket_interface__status_engine, steps 03 and 07. This one is not in a known.diff any more: the translation was changed to match Oracle, and the behaviour is now spec clause S-TICKET-065.

What happens. When a ticket moves in certain ways (resolved back to open, hot or acknowledged; a non-MCC waiting ticket expiring to hot; a deferred ticket with a future valid-until going hot), Oracle remembers the previous status in recoverable_status_id so it can be restored later. The condition that decides whether to remember it is:

IF (p_status_id IN (2, 3, 4) AND NOT v_last_public_event_type_id IN (30016)) THEN
   -- remember the current status
ELSE
   UPDATE tt.ticket SET recoverable_status_id = NULL ...
END IF;

For a ticket that has no last public event, v_last_public_event_type_id is NULL. In SQL, NULL IN (30016) is neither true nor false, and NOT of that is still unknown. An unknown condition counts as false, so Oracle takes the ELSE branch and wipes the recoverable status instead of recording it. The author almost certainly meant "any event type except 30016", which would include "no event at all".

Why it is reproduced rather than corrected. The migration's rule is that every translated routine behaves like Oracle unless a deviation is deliberately recorded. The first translation did the intuitive thing and recorded the status; the live Oracle run showed Oracle leaves it empty on exactly these tickets. I changed the translation to use the same three-valued expression so the behaviour matches, and wrote it down as S-TICKET-065 with a note that it may be unintended. Correcting it is a one-line change plus a new clause and tests, but it changes production behaviour for every ticket created without going through addevent_new, so it should be a conscious decision, not a side effect of the migration.
